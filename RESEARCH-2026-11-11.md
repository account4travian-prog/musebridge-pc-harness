## Corrections to the earlier game plan

1. **Board-backed PC access is a viable missing avenue.** The old statement that a direct gadget cannot control the PC is true for stock firmware alone. Combined with a Windows executor reachable through its existing tunnel, it can plausibly provide the requested control. This avoids making custom pairing firmware the first dependency.
2. **No stock voice on this board.** The photo shows no microphone, speaker or display. The ESP32 README explicitly excludes DevKitC-style boards from its live audio feature. Use existing phone/PC audio first; additional peripherals would be a separate build.
3. **Pairing is not the only hard part.** Windows permissions, tool discovery, command lifetimes, cancellation, reconnect behavior, results and desktop verification matter just as much.
4. **An ESP32 serial GATT bridge is not a Windows Bluetooth dongle.** Custom host software must understand it. WSL would still need USB forwarding or a Windows serial proxy; a Linux `/dev/ttyACM*` device does not appear simply by plugging USB into Windows.
5. **Lower lag is a hypothesis.** Removing scheduled-task pickup and result-file pulls should help. Cloud inference, internet latency, Muse's own tool orchestration and the ESP32 data path remain. The old 3–15 second timings are historical; no new latency numbers were measured.
6. **A button press to pair is not approval for later PC commands.** A runtime approval button, if desired, needs its own protocol, pending-action identity and expiry. Do not repurpose the long-press unpair gesture casually.
7. **The old recommendation order is stale.** Its Avenue 4 and seat-wrapper acceptance criteria conflict with the owner's correction against other local agents. Those are historical proposals, not the current backlog.
8. **Same Muse is not the same as a model API.** The Gadget connection integrates with the existing remote Muse. A new agent using a Meta model API would be a separate runtime unless a supported account/session integration establishes otherwise.

## Unknowns that only live tests can resolve

- Account eligibility, SDK token, phone pairing and server admission for the gadget/tunnel.
- Actual flash/PSRAM health, LED pin, data cable and stable power on this clone.
- LAN reachability between board and PC; client isolation/VLAN/firewall effects.
- Muse-side ability to invoke an authenticated API and retain a short tool guide in its normal workspace.
- End-to-end responsiveness, screenshot usefulness and behavior when the PC sleeps or locks.
- Exact household device models, protocols and credentials. No home-network inventory was performed.
