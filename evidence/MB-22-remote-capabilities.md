# MB-22 remote capability source audit — 2026-11-11

## Authoritative implementation follow-up — 2026-11-11

This dated source audit captured the application before the MB-15/MB-16 work. Its rows for image integration and summary handoff are historical and superseded by current implementation evidence: [MB-15 artifacts and explicit image delivery](MB-15-artifacts.md), [MB-16 continuity and live handoff](MB-16-continuity.md), and the [MB-23 integrated receipt](MB-23-integration.md). Current MuseBridge supports explicit image sends through the pinned SDK route and a bounded, summary-seeded new-chat handoff. Neither establishes native remote fork/hidden-state transfer. Current Core.send also records known server acknowledgment before local projection/run tracking; a post-ack local tracking error is surfaced as such and does not cause false send failure or resend. See MB-16 for the UUID acknowledgment regression evidence.

The capability table below is preserved as a historical source-audit snapshot. Do not use its image-send and summary-handoff integration cells as statements of current application behavior; the linked MB-15/16/23 receipts are authoritative for that behavior. The SDK/API conclusions about native fork, text steering, remote workers, compaction and usage remain limited to the pinned source audit.

## Scope and method

Read-only review of the pinned SDK source at commit `9d8cca156cdec9ea06efcf854b03dccc5ca76d42` and the current MuseBridge integration. This audit does not inspect Muse VM contents, make a live request, or infer server features from generic protocol fields. SDK method existence establishes a client route only; it does not establish this account's admission or the remote service's semantics.

## Early probes and constraints

1. **Image admission:** from a disposable project and dedicated side chat, send a generated, non-sensitive test image with a short text question through `send_image`; check the acknowledgment and whether Muse identifies its contents. Repeat only with an invalid MIME/oversize fixture locally to confirm client rejection. This remains an MB-15 integration probe, not evidence until executed.
2. **Dynamic registration:** use the existing PC identity in a controlled session. Register a harmless added test command, then verify Muse can discover and invoke it without reconnecting. Do not create a second live gadget identity. If the protocol only registers at connection setup, record that result and keep reconnect as the honest refresh boundary.
3. **True steering:** in a disposable side chat, start a long-running read-only request, send a second clearly marked message, and observe task IDs/statuses/reply ordering. Distinguish “second message accepted” from “first task interrupted or redirected.” Do not use a mutating workflow for this probe.
4. **Fork:** test any future service-documented fork route separately from a new side chat seeded with a short, source-linked summary. The latter must be labeled a new chat and cannot establish preservation of hidden state.
5. **Workers, compaction and usage:** require an explicit service-level capability/response before building controls. If exposed, use read-only tasks and record separate worker IDs, concurrency, cancellation and actual usage/compaction fields. Tool-call overlap or a long conversation alone is not proof of remote delegation or accounting.

No live session was used for this audit. The existing live text/tool receipt is limited to the routes and results it records; native fork, general steer, image acceptance, dynamic registration, remote workers, compaction and token/usage accounting remain externally unverified.
