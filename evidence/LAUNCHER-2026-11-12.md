entry, service, public port, new gadget identity or re-pairing was installed.

Both actual shortcut files were read back through Windows Shell COM: target,
working directory, connect/secondary/reuse flags and existing icon all passed.
The installer refuses conflicting foreign shortcuts and can repair its own links.
Three launcher tests passed using disposable directories; no test executed a
foreign shortcut. Start-MuseBridge.ps1 remains an offline alternative by default;
-Connect opts into saved pairing, and -ActivateExisting requests existing-window
restoration.

The app's indefinite identity lock now uses staleLockTime(0), following
[Qt's long-lived lock guidance](https://doc.qt.io/QT-6/qlockfile.html). A second
manual launch sends only an exact, bounded show message over a current-user local
pipe, rather than registering another gadget. Nine real Qt local-IPC tests passed,
including invalid/oversize inputs, fast disconnect and two queued clients. These
tests use fake callbacks, never activating a real owner window. Native startup
passed with --secondary-screen --smoke: exit 0, no stderr, disposable catalog
created; no Muse connection was requested by that smoke test.

Opening an existing window repositions it to the secondary screen before an
explicit activation request. Initial development startup still avoids activation.
If a live evaluation temporarily owns the gadget lock, the desktop app cannot
start a second connection; finish the evaluation before opening the normal app.
Runtime connection and broader MB-29 live acceptance are separate from this
launcher verification.
